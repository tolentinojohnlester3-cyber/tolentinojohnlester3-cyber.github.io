How to fix sitemap "Couldn't fetch" in Google Search Console

You submitted your XML sitemap in Google Search Console and the status says Couldn't fetch. That usually means Google tried to open the file and hit a 404, 500, timeout, or property mismatch — not that your whole site is broken. This guide walks through the fixes in order.

What "Couldn't fetch" means

In Google Search Console, the sitemap report shows whether Google could download and read your XML sitemap. Couldn't fetch means the request failed before Google could process the URLs inside it.

Common causes:

  • The sitemap file returns 404 Not Found (not uploaded yet or wrong path)
  • A temporary 500 server error during deploy or hosting glitch
  • The sitemap was submitted to the wrong GSC property (http vs https, www vs non-www)
  • robots.txt or firewall rules block Googlebot from the sitemap URL
  • The file is not valid XML or lists URLs on a different domain
Important: "Couldn't fetch" is about the sitemap file. Your pages can still be indexed through internal links. But fixing the sitemap helps Google discover new and updated URLs faster.

5-minute fix checklist

Run through these steps before diving deeper:

  • Open your sitemap URL in a private browser tab — you should see XML, not a 404 or error page
  • Confirm you are in the correct Search Console property (exact protocol and hostname)
  • In GSC → Sitemaps, submit only sitemap.xml (for URL-prefix properties)
  • Check /robots.txt — make sure it does not block /sitemap.xml
  • Wait 5–10 minutes after any deploy, then click Resubmit

Verify the sitemap is live

Your sitemap must be publicly reachable. Test the exact URL you declare in robots.txt.

Example for a GitHub Pages site:

  • Sitemap: https://yoursite.github.io/sitemap.xml
  • Robots: https://yoursite.github.io/robots.txt

Quick HTTP status check

Use Chrome DevTools → Network, or run in terminal:

curl -I https://yoursite.com/sitemap.xml

You want HTTP 200. A 301 redirect to the correct HTTPS URL is usually fine. 404 and 500 are not.

File not on the server yet

This is the most common cause I see on static sites and GitHub Pages: the sitemap exists locally on your computer but was never pushed to production. After upload, wait a few minutes for the host to rebuild, then test the live URL again.

Match your GSC property

Search Console properties are strict about URL format. If your live site is:

https://example.com

…then your sitemap URLs inside the file must use https://example.com/..., and you must submit the sitemap under the https://example.com property — not http://, not https://www.example.com unless that is your canonical host.

Submit the sitemap correctly

In Google Search Console:

  1. Open your property
  2. Go to Sitemaps (under Indexing)
  3. Enter sitemap.xml in the "Add a new sitemap" field
  4. Click Submit

For a URL-prefix property, GSC already knows your domain — you only need the path. Submitting the full URL twice sometimes causes confusion; stick to sitemap.xml unless you use a sitemap index at a different path.

WordPress sitemap paths

  • Yoast / Rank Math: usually sitemap_index.xml
  • WordPress core (5.5+): wp-sitemap.xml
  • All in One SEO: sitemap.xml

Submit the path your plugin actually generates — open it in the browser first to confirm.

Check robots.txt and blocking

Your robots.txt should allow Googlebot to fetch the sitemap. A typical setup:

User-agent: *
Allow: /

Sitemap: https://yoursite.com/sitemap.xml

Problems to watch for:

  • Disallow: /sitemap.xml — remove this
  • Sitemap line pointing to the wrong domain or old staging URL
  • CDN or security plugin blocking Googlebot with a challenge page
  • Password protection on the whole site (common on staging)

The sitemap line in robots.txt is a hint for crawlers; the URL must still return 200 when fetched directly.

Fix invalid XML and bad URLs

If Google can fetch the file but still reports errors, check the XML itself:

  • Starts with <?xml version="1.0" encoding="UTF-8"?>
  • Uses <urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  • Every <loc> is a full absolute URL (https://...)
  • No broken characters or copy-paste corruption
  • URLs in the sitemap return 200 (not 404 or redirect chains to unrelated domains)

Validate with an XML sitemap validator or Search Console's URL Inspection on a few listed pages.

WordPress, static sites, and GitHub Pages

WordPress

  • Flush permalinks (Settings → Permalinks → Save) if sitemap 404s
  • Disable conflicting SEO plugins — only one should generate the sitemap
  • Exclude noindex staging URLs from the sitemap

Static / custom HTML sites

  • Place sitemap.xml at the site root (same level as index.html)
  • Add a .nojekyll file on GitHub Pages if Jekyll processing causes issues
  • Regenerate the sitemap when you publish new blog posts

GitHub Pages

Files must live in the repo root (or your configured /docs folder), not inside an un-deployed subfolder. After push, Pages can take 2–5 minutes to rebuild. A brief 500 error right after deploy is normal — resubmit once the URL loads cleanly.

FAQ

Does "Couldn't fetch" mean my site is deindexed?

No. It means Google could not download the sitemap file. Your pages may still be indexed through links. Fix the sitemap so Google discovers URLs more reliably.

How long after fixing should I wait?

Resubmit in Search Console after the live sitemap returns 200. Status often updates within hours, but allow up to 48 hours before assuming something else is wrong.

Should I submit sitemap.xml or the full URL?

For a URL-prefix property, enter sitemap.xml. For a Domain property, you can use the full URL https://yoursite.com/sitemap.xml.

Can I delete and resubmit the sitemap?

Yes. Remove the failed entry, confirm the live file works, then submit again. This is often the fastest way to clear a stale error after a deploy.

Do I need a sitemap for a small site?

Not strictly — Google can crawl small sites through links. Still, a sitemap is cheap insurance for new pages, blog posts, and after migrations. I recommend one for every site I manage.
